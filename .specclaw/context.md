# Project Context

_Last updated: 2026-11-20 after 003-d10-d11-exam-day-swagger and 004-m1-exam-conventions-and-guides_

## Architecture Overview
- A practice pack for the 5COSC019W OOP Lab-Based Practical. Stack: Java 17, Spring Boot 3.3.5, Maven wrapper 3.9.9.
- **The real exam** (official exam-day instructions, 2026-11-19) is 120 minutes: 110 to code and test, then the final 10 only for the ZIP and the Blackboard upload. It runs JDK 25 + IntelliJ Ultimate, in the order Q1 Section A (Java/OOP) → Q2 Section B (Spring/REST) → Section C (functional verification). The starter includes Swagger UI, and the student creates exactly ONE new class. The module team's own mock uses Spring Boot 4.1.1. The pack stays on JDK 17 / Boot 3.3.5, because JDK 25 isn't on the dev PC; lessons say the code is the same.
- **Drills.** Each drill (`drills/dNN-*`) is a module of the root aggregator `pom.xml` (`edu.practice:oop-practice`). It contains:
  - `LESSON.md`, with front matter and five sections: idea, worked example, task, hints, viva.
  - A starter in `src/main`.
  - Tests in `src/test`.
- **Papers.** Each project in `mock-papers/*` and `past-papers/*` is a standalone Spring Boot project with its own wrapper and a `PAPER.md`.
  - Marking tests live outside the projects, in `marking/<id>/src/test/java/marking/`.
  - `marking/Mark.java` copies them into the attempt and scores it.
- **Branches.**
  - `main` and the feature branch hold the starters, lessons, tests and marking.
  - `solutions` is `main` plus the completed `src/main` files, and nothing else.
- **Guides.** `guides/EXAM-DAY.md` (exam-day guide) and `guides/REFRESHER.md` (concept refresher) render to `guides/*.pdf` as the `guide` kind of the PDF pipeline, and are checked like papers.
- **PDFs.** Each drill has a `LESSON.pdf` (no hints, viva questions only) and a `HINTS.pdf` (numbered hints, then viva answers) next to `LESSON.md`. Each paper has a `PAPER.pdf`. They're generated by `scripts/build-pdfs.sh` / `.cmd` (Node, under `scripts/pdf/`) and committed. The Markdown is always the source.
- **Site files.** `papers/<id>.md` is generated from `LESSON.md` or `PAPER.md` by `scripts/sync-papers.sh`, for the future study site.

## Coding Style & Conventions
- **New or reworked papers follow the module mock's conventions (M1 does):**
  - packages `controller / exception / model / repository / service`, with no `dto` package
  - request and response types are **plain classes with getters, not records**; request classes also get a no-arg constructor + setters for Jackson
  - `GlobalExceptionHandler` + `ErrorResponse(code, message)` in `exception`
  - no `/api` prefix, port 8080
  - Swagger via springdoc `2.6.0` at `/swagger-ui.html`
- **The older drills and P1–P3** still use `model / dto / repo / service / controller / error`, records for DTOs and `ApiError`. Leave them unless a change says so.
- **Everywhere:** an in-memory `ConcurrentHashMap` repository, constructor injection, and a `@RestControllerAdvice` that maps IllegalArgumentException → 400 `BAD_REQUEST`, NotFound → 404 `NOT_FOUND`, and Conflict → 409 `CONFLICT`.
- Starter TODOs are written `// TODO dNN-n: …`. Unfinished method bodies throw `UnsupportedOperationException("dNN: …")`.
- Drill tests use numbered names: `@DisplayName("1. …")`.
- Marking test methods end in `_m<N>`, where N is the marks. The marks in `Task1Test`…`Task4Test` and the functional class must sum to exactly 18/22/20/20/20. The functional class is `SectionCTest` for m1 and `SectionBTest` for p1–p3; `Mark.java` swaps the allocation key per paper.
- With plain request classes there's no `equals`, so Mockito `verify(service).x(new Req(...))` fails. Match with `argThat` on the getters instead (see M1 `Task4Test.bodyIs`).

## Key Patterns
- **Classes the student creates** are reached through the `Reflect` helper (`templates/Reflect.java`). This keeps starters compiling, and a missing class costs only its own marks.
- **Marking isolates each task:**
  - Task 2/3 service tests use stub subclasses and stub repositories.
  - Task 4 tests compare against the app's own service bean or a `@MockBean`.
  - Error mapping is tested through a controller that only throws.
- **Section B checks** use `@SpringBootTest(classes = <App>.class, webEnvironment = RANDOM_PORT)` with `TestRestTemplate` and `@DirtiesContext`. The `classes =` part is required because the `marking` package isn't under the app's package.
- **Source scans** enforce "no type checks". `SourceScan` strips comments, then bans `instanceof`, casts or `.class` of concrete types, and other `getClass()` uses. `getClass().getSimpleName()` is allowed as a type label.
- **Solution workflow:**
  1. Build the full solution first.
  2. Stage the changed `src/main` files in `.staging/solutions/` (gitignored).
  3. Turn the project back into the starter.
  4. The lead commits the starter, merges the build branch into `solutions`, and overlays the staged files.

## Technology Decisions
- The PDF renderer is Node ESM in `scripts/pdf/`: `marked`, `highlight.js`, `js-yaml`, and `puppeteer-core` driving the installed Chrome or Edge (`CHROME_PATH` overrides). `pdfjs-dist` is used by `check.mjs`. All versions are pinned exactly and `node_modules` is gitignored. Nothing is added to the Maven build.
- A Maven wrapper ships in every project, so no global Maven install is needed.
- The marking runner is single-file Java (`java marking/Mark.java`). It works on any platform with only JDK 17. `mark.sh` and `mark.cmd` are thin wrappers.
- IntelliJ's HTTP Client is Ultimate-only, so the functional checks are covered by tests. `requests.http` is a bonus. Lessons teach **Swagger UI** as the main checking tool, with curl as the fallback.
- Dependencies are `spring-boot-starter-web`, `spring-boot-starter-test`, and `springdoc-openapi-starter-webmvc-ui` **2.6.0** in d10, d11 and M1. springdoc 2.8.x needs Boot 3.4+ and crashes on 3.3.5 (`NoClassDefFoundError: LiteWebJarsResourceResolver`).

## Constraints
- After editing any `LESSON.md` or `PAPER.md`, run `bash scripts/build-pdfs.sh` and commit the PDFs. Its `check.mjs` fails if a hint or viva answer leaks into a `LESSON.pdf`.
- Don't use `position: relative/absolute` in `scripts/pdf/style.css`. Chrome paints positioned elements last, which puts their text out of reading order in the PDF and breaks `check.mjs`. Extracted PDF text needs NFKC normalisation (the fl/fi ligatures).
- Never put solution bodies on `main` or the feature branch. `solutions` may differ only under `src/main/` (selfcheck AC-10).
- After **any** commit on the content branch, run `git switch solutions && git merge <branch>`. Never merge in the other direction. Selfcheck fails if `solutions` is behind.
- Untouched starters must score ≤ 20/100, and solutions exactly 100. Test every rule with at least 2 inputs, including one that isn't shown in the paper or lesson.
- Scenarios must be fictional and new. Never claim to predict the real exam.
- Don't run `specclaw-build finalize` with `branch-per-change`. It merges into `main` locally and deletes the branch, which bypasses verify and the PR. Use `specclaw-set-phase … build done` after selfcheck passes.
- The student's working tree is usually dirty with their own attempts, including staged files. Never commit from it with a plain `git commit`, and never use `specclaw-build commit` (no pathspec). Build, verify and open PRs from git worktrees, and commit with explicit pathspecs.
- The drill jars aren't runnable on their own. Smoke-test a drill with `./mvnw -pl drills/<d> spring-boot:run -Dspring-boot.run.arguments=--server.port=<p>`.
- An absolute `<relativePath>` doesn't resolve on Windows. To test a drill outside the repo, copy the root pom next to it.
