## Scenario

A compute cluster accepts batch workloads and deadline-bound workloads. Each job requires CPU cores, memory, a number of discrete time ticks and a release time. Your scheduler must create non-overlapping, resource-feasible allocations, support dry-run previews and commit plans without double-booking.

Seed after Task 2: `BatchWorkload(1,2,4000,3,0)`, `DeadlineWorkload(2,4,6000,2,0,4)`, `BatchWorkload(3,2,2000,2,1)`, `DeadlineWorkload(4,3,6000,3,1,6)`. Each reservation uses a half-open interval `[startTick, endTickExclusive)`.

## Task 1 – Implement aging-aware BatchWorkload [18 marks, LO1]

- **4 marks:** implement `BatchWorkload extends Workload`; initialise inherited ID, resource, duration and release fields through the parent constructor.
- **8 marks:** `urgencyAt(nowTick)` = 100 + 2×max(0, nowTick−releaseTick), rejecting negative nowTick and preventing overflow.
- **6 marks:** `latestStartTick()` returns `Integer.MAX_VALUE` and polymorphic dispatch remains through `Workload` references.

## Task 2 – DeadlineWorkload and dynamic ranking [22 marks, LO1]

- **7 marks:** introduce `DeadlineWorkload` with `deadlineTick`, constructor and getter.
- **7 marks:** `urgencyAt(nowTick)` = 1000 − 5×max(0, deadlineTick−nowTick−durationTicks), using safe arithmetic. `latestStartTick()` = deadlineTick−durationTicks.
- **8 marks:** implement `SchedulerService.ranked(nowTick)`, sorting all workloads by urgency at that tick DESC and ID ASC; implement `urgency(id, nowTick)` and 404 on missing ID.

## Task 3 – Implement deterministic preview scheduling [20 marks, LO2]

- **5 marks:** validate `PlanRequest`: nowTick ∈ [0, 1,000,000], horizon ∈ [1, 24], cpuCapacity ∈ [1, 64], memoryCapacity ∈ [1, 1,000,000].
- **5 marks:** process workloads in ranked order and determine earliest start = max(nowTick, releaseTick), latest allowable start = min(nowTick+horizon−durationTicks, latestStartTick()).
- **5 marks:** search earliest feasible integer start tick. For every occupied tick, existing confirmed reservations PLUS assignments selected during this preview must not exceed either CPU or memory capacity.
- **5 marks:** produce `SchedulePlan` with selected reservations and rejected records in ranked order; use reason `RELEASE_OUTSIDE_WINDOW`, `DEADLINE`, `EXCEEDS_CAPACITY` or `NO_SLOT` as appropriate. Preview must not mutate confirmed state.

## Task 4 – Commit semantics, conflict control and REST API [20 marks, LO2]

- **4 marks:** implement `GET /api/workloads/{id}/urgency?nowTick=...`, `GET /ranked?nowTick=...`, `POST /preview` and `GET /reservations`.
- **4 marks:** implement `POST /commit` accepting `CommitRequest(runKey, nowTick, horizon, cpuCapacity, memoryCapacity)`; on a new runKey persist selected assignments atomically to confirmed reservations.
- **7 marks:** identical retry (same runKey, same request) must return the identical original plan without duplicating reservations; same runKey with changed values must produce HTTP 409 / `ApiError(code="CONFLICT")`.
- **5 marks:** handle invalid inputs with HTTP 400 and unknown workload IDs with HTTP 404; ensure deterministic ordering in `GET /reservations`.

## Illustrative calculations and input

- With request `{"nowTick":0,"horizon":6,"cpuCapacity":6,"memoryCapacity":10000}`, deadline workload 2 is considered ahead of batch workload 1.
- The scheduler must check both resource dimensions on every tick, not merely at a job's start tick.
- POSTing an identical `/commit` request twice must leave the number of confirmed reservations unchanged.
